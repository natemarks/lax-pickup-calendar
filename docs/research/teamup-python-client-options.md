# Teamup Python Client Options & Machine-Readable API Spec

## Summary

**No actively-maintained, trustworthy Python client library exists for Teamup's Calendar API.** The three candidates found on PyPI/GitHub are either years-stale, read-only, or have no discoverable source repository at all (see Findings §1). **Recommendation: call Teamup's REST API directly via `requests`.** This is a safe choice — auth is a single static header (`Teamup-Token`), and nothing in Teamup's own docs makes direct `requests` calls impractical.

**The biggest finding of this research: Teamup's OpenAPI 3.0 spec is directly fetchable as raw YAML**, at a URL linked from Teamup's own API overview page (found via a raw-HTML grep of the Authentication doc page, the same technique the prior `hugo-natenite.net` research tried twice and came up empty — this time it worked because the *Authentication* page, unlike the JS-only doc pages checked before, happens to server-side-render its markdown, and that rendered page's Markdown links directly to the spec file):

```
https://stoplight.io/api/v1/projects/teamup/api/nodes/reference/generated_docs_public.yaml
```

This is a genuine, complete (6,661-line, ~227KB) `openapi: 3.0.0` document — not a page shell, not a snippet. It was fetched and parsed directly in this research (`curl` + line/grep inspection) and **directly confirms every field name the prior research could only source from search snippets**: `remote_id`, `rrule`, and `ristart_dt` all exist exactly as described in `hugo-natenite.net/HOSTED.md`, with full descriptions, on the Create/Update/Delete/Get-events endpoints. This should let [Confirm Teamup's real API behavior](../../.scratch/teamup-calendar-sync/issues/02-confirm-teamup-api-behavior.md) skip straight to reading a real schema instead of relying on JS-rendered pages or snippet text.

Auth scheme: static API-key header (`Teamup-Token`), no OAuth required for basic use. Pagination: only the *search* endpoint supports `offset`/`limit`; the main list-events endpoint is bounded by date range instead. No documented numeric rate limit — Teamup's own text says they'll contact you before throttling. None of this blocks a direct-`requests` implementation.

## Findings

### 1. Python client libraries surveyed

None qualify as "actively maintained and trustworthy." All four candidates found (via PyPI search, GitHub search, and the GitHub API) are summarized below, checked against their own PyPI pages, GitHub repos, and the GitHub API (commit/release/license metadata) directly.

| Library | Source | License | Last activity | Covers create/update/delete/list? |
|---|---|---|---|---|
| **pyTeamUp** ([PyPI](https://pypi.org/project/pyTeamUp/), [GitHub](https://github.com/Djones4822/pyTeamUp)) | PyPI + GitHub | MIT | Last commit **2021-12-08**; last release `v0.1.5a-ALPHA` (alpha-tagged) | Yes — create/update/delete events, list subcalendars/events, batch-update mode |
| **teamup-connect** ([PyPI](https://pypi.org/project/teamup-connect/)) | PyPI only, **no discoverable GitHub repo** | MIT (per PyPI metadata) | Latest release `0.3.0`, uploaded **2024-08-19**; all 4 releases cluster within a 10-day window in Aug 2024, none since | Partial — README documents `get_calendar`, `get_subcalendars`, `create_calendar_event`, `delete_calendar_event`, `get_calendar_events`; no documented `update` method |
| **teamup** ([GitHub — clerie/teamup](https://github.com/clerie/teamup)) | GitHub only, not on PyPI | MIT | Last commit **2018-09-07**; only 3 commits total, no tags/releases | **No** — read-only (`get()` only); README's own TODO list explicitly says "Write access" is incomplete |
| **teamup** ([GitHub — chris-santiago/teamup](https://github.com/chris-santiago/teamup)) | GitHub only, not on PyPI | **None** (no license file/classifier) | Last push **2023-03-12**; 0 stars | Not evaluated further — no license makes it unusable without contacting the author |

Details, each confirmed directly against the primary source:

- **pyTeamUp**: PyPI metadata ([pypi.org/pypi/pyTeamUp/json](https://pypi.org/pypi/pyTeamUp/json), fetched directly) confirms MIT license (`classifiers: ["License :: OSI Approved :: MIT License", ...]`), version `0.1.4a0` as the "current" PyPI release with a release history from `0.1.0a1` (2018-11-30) through `0.1.4a0` (2021-11-29). The [GitHub repo](https://github.com/Djones4822/pyTeamUp) (checked via the GitHub API: `pushed_at`, `archived`, tags) shows `pushed_at: 2021-12-08T22:56:52Z`, `archived: false`, 2 tags (`v0.1.4a`, `v0.1.5a-ALPHA`), 6 stars, 1 open issue. The README (fetched directly) states outright: "In early stages, only has event and calendar objects implemented" and documents a known gap — an *undocumented* Teamup API change around the `attachment` event field that the library can read but not write. **Nearly 4 years stale as of this research (Sept 2026), self-described as early-stage/alpha, but it is the most complete and best-documented of the four** — it's the only one with a batch-update mode and explicit create/update/delete coverage.
- **teamup-connect**: PyPI JSON ([pypi.org/pypi/teamup-connect/json](https://pypi.org/pypi/teamup-connect/json), fetched directly) shows `project_urls: None` — no homepage/repository link is published at all, and a targeted web search for `"teamup-connect" OR "teamup_connect" github` turned up no source repository anywhere. This is a hard trust blocker: there's no way to audit the code, check commit history, or verify test coverage. `requires_python: >=3.10`. Its README (embedded in the PyPI `description` field, fetched directly) documents `create_calendar_event`/`delete_calendar_event`/`get_calendar_events`/`get_subcalendars`/`get_calendar`, but no `update` method is shown in the documented usage — update/list-changes coverage is unconfirmed.
- **clerie/teamup**: GitHub API metadata confirms `pushed_at: 2018-09-07T18:06:22Z`, 0 stars, 0 forks — essentially untouched since creation. README (fetched directly) explicitly lists "Write access" under a TODO/incomplete section, so create/update/delete are not implemented at all — this library can only `GET`.
- **chris-santiago/teamup**: found via GitHub's repository search API (`teamup calendar api language:python`), `pushed_at: 2023-03-12T03:36:27Z`, `license: None` (no `LICENSE` file or SPDX classifier detected by GitHub), 0 stars. Not on PyPI. Given no license is attached, it cannot be safely depended on regardless of code quality — not evaluated in further detail.

**Conclusion**: none of the four meets a reasonable maintenance/trust bar for a sync engine that will run repeatedly against a real calendar. The closest thing to "actively maintained" (teamup-connect, last touched 13 months before this research) has no visible source at all. **Recommendation stands: implement directly against the REST API with `requests`.**

### 2. Direct REST API via `requests` — no blockers found

All three sub-questions (auth, pagination, rate limits) are answered directly from Teamup's own OpenAPI spec (see §3) plus the Authentication doc page ([apidocs.teamup.com/docs/api/e60b71a05cf57-authentication](https://apidocs.teamup.com/docs/api/e60b71a05cf57-authentication)) — which, unlike the specific `create-an-event`/`update-an-event` pages the prior research tried, **did fully server-side render** when fetched directly in this research (`curl -A "Mozilla/5.0"`, 455,942 bytes returned, containing the full rendered guide markdown, not a page shell).

- **Auth scheme**: a static API key sent as an HTTP header, confirmed both in the OpenAPI spec's `securitySchemes` block and in the Authentication page's own text:
  ```yaml
  securitySchemes:
    teamup_api_key:
      type: apiKey
      description: API key header (required)
      name: Teamup-Token
      in: header
    user_authentication:
      type: http
      description: |
        Authorization header for logged in users.
        This needs only to be used when the calendarKey does not provide the required access-rights.
      scheme: bearer
  ```
  The Authentication page states plainly: "Every request to the API must include an API key in a request header," shown as `curl "https://api.teamup.com/{calendarKey}/events" -H "Teamup-Token: API_KEY"`. A separate, optional `/auth/tokens` endpoint exists for obtaining a bearer token via username/password login, but is "only necessary when the calendarKey that you are using to access the API is not providing the required access rights" — not needed for a server-side sync engine using a normal API key + calendar key. There's also a `GET /check-access` endpoint for validating a key, and an optional `Teamup-Password` header for password-protected calendars. All of this maps trivially onto `requests` (`requests.get(url, headers={"Teamup-Token": api_key})`) — no SDK-specific auth flow (no OAuth dance) is required.
- **Pagination**: the main **Get events** endpoint (`GET /{calendarKeyOrId}/events`, `operationId: get_list_events`) has *no* offset/limit pagination — results are instead bounded by the `startDate`/`endDate` query parameters (defaulting to just "today" if omitted), so a full sync would iterate by date range rather than by page. The separate **Search events** endpoint (`GET /{calendarKeyOrId}/events?query={query}`) *does* document real offset/limit paging: "This endpoint supports the paging of results. Use parameter `limit` to specify the size of a result set and parameter `offset` to specify which page to read," with `offset` (default `0`) and `limit` query parameters. There's also a **Get changed events** endpoint (`GET /{calendarKeyOrId}/events?modifiedSince={modifiedSince}`) for incremental diffing — "A timestamp at most 30 days into the past. All events that were created, updated or deleted after this time will be returned" — which is directly relevant to this project's planned full-sync/diff logic (deleted events are represented via a `delete_dt` field in the response, not a separate endpoint). None of this is a blocker for `requests`; it's a straightforward query-param loop.
- **Rate limits**: **no documented numeric limit was found anywhere** (checked the OpenAPI spec text, the Authentication page's full rendered text, and the API-usage-best-practices page's SEO meta description — the best-practices page itself would not fully server-side render even via direct `curl`, same JS-shell problem the prior research hit). What *is* documented, via the best-practices page's `<meta name="description">` tag (SSR'd for SEO even though the page body isn't, fetched directly from [apidocs.teamup.com/docs/api/ZG9jOjI4Mzk0ODEw-api-usage-best-practices](https://apidocs.teamup.com/docs/api/ZG9jOjI4Mzk0ODEw-api-usage-best-practices)): *"If your API use case requires automatic periodic syncing with Teamup Calendar, it should not sync too frequently and make reasonable use of API calls."* A fuller paraphrase of this same page's guidance (consistent with, and not contradicted by, the meta-description text; cross-checked via web search snippets of the same URL rather than the rendered body) is that Teamup will proactively contact a registered API-key holder about problems (high error rate, inefficient use, excessive requests) *before* imposing filtering/rate limiting — i.e. there is no hard published requests-per-minute ceiling, but the guidance is explicitly "don't sync too often." For this project's one-way full-sync engine (run manually or on a coarse schedule, not per-request-per-user), this poses no practical blocker — a single sync run makes on the order of tens-to-low-hundreds of calls, not a high-frequency polling loop.

### 3. Machine-readable spec — found and directly fetched

**Yes — a full OpenAPI 3.0 spec exists and is directly fetchable**, at:

```
https://stoplight.io/api/v1/projects/teamup/api/nodes/reference/generated_docs_public.yaml
```

This is the answer to the exact gap `hugo-natenite.net/HOSTED.md` flagged: its two prior attempts to fetch `apidocs.teamup.com`'s Stoplight-rendered pages (including a raw-HTML grep for `remote_id`/`rrule` across ~450KB of fetched HTML) found nothing, because those *specific* pages (`create-an-event`, `update-an-event`) are pure client-side-rendered page shells with no server-rendered content. This research instead fetched the **Authentication** doc page directly (`curl -A "Mozilla/5.0" https://apidocs.teamup.com/docs/api/e60b71a05cf57-authentication`), which — unlike the endpoint-schema pages — *does* server-render its full markdown body, and that body's rendered text links out to: "You can also [download the latest OpenAPI specification](https://stoplight.io/api/v1/projects/teamup/api/nodes/reference/generated_docs_public.yaml)." Fetching that URL directly returns a real `openapi: 3.0.0` document (HTTP 200, 231,922 bytes / 6,661 lines) with `info.title: Teamup`, `servers: [{url: 'https://api.teamup.com'}]`, and a `paths:` section covering every endpoint referenced in this doc (Events, Sub-Calendars, Configuration, Attachments, Event-Comments, Reminders, Event-Signups, Access Keys, Notifications, Activity-Stream, Authenticate, Users, Calendars, Dashboard).

Directly confirmed from this spec (not snippets — actual YAML read and grepped in this research):

- **`Create an event`** — `POST /{calendarKeyOrId}/events`, request body `Event.create` / `Event.createRecurring` (a `oneOf`), response `Event.write_response`.
- **`Update an event`** — `PUT /{calendarKeyOrId}/events/{eventId}`. The description documents **three addressing modes**, quoted directly from the spec: "1. eventId in the path parameters + event's `id` field in the JSON request body (must match) / 2. event's `remote_id` + `ristart_dt` (for recurring events) fields in the JSON request body / 3. eventId in path set to 0 and `remoteId` + `startTime` (for recurring events) as query parameters." This is the first primary-source confirmation (not a search snippet) of the `remote_id`/`ristart_dt` upsert-by-your-own-id path this project's Destination assumes.
- **`Delete an event`** — `DELETE /{calendarKeyOrId}/events/{eventId}`, same `remote_id`+`ristart_dt` addressing mode as an alternative to path-based `eventId`. An optional `version` query parameter supports soft-locking (delete only succeeds if it matches the stored version).
- **`Get events`** (list) — `GET /{calendarKeyOrId}/events`, filtered by `startDate`/`endDate`/`subcalendarId[]`/`tz`; the description states plainly that for recurring events "the recurrence rule is evaluated and all event instances that fall between the given start and end date are returned" — i.e. querying by date range expands recurring series into instances (relevant if this project ever needs occurrence-level reads, separate from the single-object-with-`rrule` write model).
- **`Get changed events`** — `GET /{calendarKeyOrId}/events?modifiedSince={modifiedSince}`, for incremental change detection, with deletions represented via a `delete_dt` field rather than omission from the response.
- **Field-level schema** (`Event.create`, `Event.update`, etc., `components/schemas` section, lines ~2500–3700 of the fetched YAML): confirms `remote_id` ("title: Unique (per calendar) remote identifier — description: This can be used to link Teamup events to events in third-party applications," nullable string), `rrule` ("In iCal RRULE format, see: https://www.kanzaki.com/docs/ical/rrule.html"), `ristart_dt`, `subcalendar_ids` / `subcalendar_remote_ids` (a parallel remote-id field for sub-calendars, not previously flagged in the prior research), `title`, `location`, `notes` (markdown or HTML, selectable via an `inputFormat` query param), `start_dt`/`end_dt`, and `all_day` — this is enough for [ticket 02](../../.scratch/teamup-calendar-sync/issues/02-confirm-teamup-api-behavior.md) to build a concrete field-mapping table directly from a primary source instead of inference.

**Postman collection**: also exists — [Teamup Calendar API Examples](https://www.postman.com/teamup-calendar/teamup-calendar-public-workspace/collection/9dxuvwb/teamup-calendar-api-examples) on the Postman API Network, linked from the same Authentication page text ("there is also a Postman API and Collection available"). **This research located it and confirmed the link resolves (HTTP 200)**, but could not read its actual request/endpoint contents directly — Postman's public-collection viewer page is itself a JS-rendered React SPA (fetched raw HTML was ~100KB with no endpoint names present in the markup). Since the OpenAPI YAML above was fully and directly readable, it supersedes the Postman collection as this project's reference and the Postman collection wasn't pursued further (e.g. via Postman's own export API, which would likely require a Postman account/API key — out of scope for this pure-research ticket).

## Open Questions / Unverified

- **Exact numeric rate limit, if any, remains undocumented.** Teamup's own "API Usage Best Practices" page could not be fully server-side rendered even via direct `curl` in this research (same JS-shell problem as the pages the prior `hugo-natenite.net` research hit) — only its SEO `<meta name="description">` tag was recovered directly. The fuller "we'll contact you before rate-limiting" framing is sourced from web-search snippets of that same page's body text, not a page this research read in full — treat it as a WebSearch-corroborated claim, not a directly-confirmed quote. If precise limits matter later, request them directly from `support@teamup.com` (the contact address given in the spec's own `info.contact`) or try fetching that page with a headless browser.
- **Whether repeat-calling `POST /{calendarKeyOrId}/events` with the same `remote_id` auto-upserts, or whether a caller must look up by `remote_id` first (e.g. via `Get changed events` or `Get an event`) and then branch between POST/PUT, is not addressed by the OpenAPI spec's `Create an event` description** — the spec documents `remote_id` as an addressable *lookup* key for Update/Delete, but the Create endpoint's own text doesn't state what happens if a `remote_id` already in use is submitted again via POST. This is the same class of open question the prior research flagged for Google Calendar's `iCalUID` — resolving it belongs to [ticket 02](../../.scratch/teamup-calendar-sync/issues/02-confirm-teamup-api-behavior.md)'s live-API testing, not this library-survey ticket. This research's contribution is narrowing it to a precise, spec-grounded question rather than leaving the underlying field names themselves in doubt.
- **The Postman collection's actual request bodies/examples were not read** (see §3) — if a future ticket wants worked request/response examples rather than just the schema, it would need either a headless-browser fetch of the Postman viewer or Postman's own collection-export API.
- **`subcalendar_remote_ids`** (found alongside `remote_id` in the schema, a parallel remote-identifier field for sub-calendars) was not previously mentioned in `hugo-natenite.net/HOSTED.md`'s research and isn't otherwise investigated here — worth a look if this project ever needs to address sub-calendars by an external id rather than Teamup's internal integer ids, though the Destination's "single flat calendar" decision means it's likely unnecessary for this effort.
