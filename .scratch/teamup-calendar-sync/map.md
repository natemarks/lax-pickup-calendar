# Teamup Calendar Sync Engine

Label: wayfinder:map

## Destination

`lax-pickup-calendar` becomes the new home for calendar-management logic (eventually replacing `hugo-natenite.net`'s `data/events.json` -> `scripts/sync_calendar.py` -> `static/events.ics` pipeline outright). This effort builds a Python sync engine that reads `lax-pickup-calendar/data/events.json` (already copied in from `hugo-natenite.net`) and performs a **one-way, idempotent, full sync** into a real Teamup calendar the user already controls (calendar + API key both already exist) -- creating, updating, and **deleting** events so Teamup's state always exactly matches the JSON's state, keyed by the JSON's stable `id` (mapped to Teamup's `remote_id` field, if it works as `hugo-natenite.net/HOSTED.md`'s research suggests). Weekly events are represented as a single Teamup event + `rrule`, not one row per occurrence -- mirroring the original spec's own recurrence model.

Follows the original spec's own de-risking shape: a small, direct, hand-verified API test (including one recurring event) *before* the general "sync everything" engine is built, since `HOSTED.md` flagged Teamup's real upsert/`rrule` behavior as **unconfirmed** (its core API schema pages are JS-rendered Stoplight docs that prior research could not directly fetch -- the `remote_id`/`rrule` claims rest on search snippets only).

**Done** = the real Teamup calendar is populated and matches the real `data/events.json` (not just "tests pass") -- with tests covering the sync/generator logic itself, mirroring the original spec's Phase 3 testing approach (assert output/payload shape directly, not by round-tripping through Teamup or a third-party parser).

## Notes

- **Execution is in scope for this map**, not just decisions -- the destination is an executed outcome ("the real calendar is populated"), not a spec handoff. Tickets may include actual implementation/build work once the open API questions are resolved, per the `/wayfinder` skill's Notes-override.
- Source spec: `docs/specs/public-lacrosse-calendar-site.md` (same spec `hugo-natenite.net` already implemented for Phases 1-3).
- Prior research to consult: `hugo-natenite.net/HOSTED.md` (hosted-calendar-service comparison, Teamup section) and `hugo-natenite.net/docs/research/` (calendar-subscribe-links.md, google-calendar-csv-import.md).
- Reference implementation for JSON schema and recurrence/one-off/incomplete-entry handling conventions: `hugo-natenite.net/scripts/sync_calendar.py` and `hugo-natenite.net/data/events.example.json`.
- This project's static analysis/testing conventions (Makefile `static`/`unit`/`integration` targets, pinned deps, pre-commit gitleaks) are already scaffolded -- see `CLAUDE.md`. Use `make integration` framing for anything that needs live Teamup credentials.
- Standing decisions for this effort (settled during destination-naming, not separate tickets):
  - One-way sync only: JSON is sole source of truth; Teamup is never read back to modify the JSON (no two-way reconciliation).
  - Full sync semantics: an event removed from the JSON gets **deleted** from Teamup, not just left orphaned.
  - Single flat Teamup calendar -- no sub-calendar routing needed.
  - Credentials are supplied via a gitignored `.env` file at the repo root (`TEAMUP_TOKEN`, `TEAMUP_CALENDAR_KEY`), loaded as environment variables -- not a JSON/YAML config file. `TEAMUP_CALENDAR_KEY` holds a "Modify"-permission Calendar Link key (from [ticket 05](issues/05-write-capable-access-key.md)), scoped to just this one calendar; full read+write access confirmed.
  - **Auth model decision**: Teamup's OpenAPI spec documents a second scheme (`user_authentication`, bearer token via `/auth/tokens` username/password login) as an alternative to a Calendar Link key. Deliberately **not** used -- a login-based token is still a bearer credential once obtained, but with much larger blast radius if leaked (whole account vs. one calendar at one permission level), plus refresh/expiry complexity for no real security gain on a personal project. Sticking with the Calendar Link key.
  - **Incident note**: the first Modify-permission link's key was pasted directly into the planning chat while being reported, which exposed it outside `.env`. Treated as compromised; tracker files were retroactively redacted of raw key values. Going forward, credential values are set directly in `.env`, never pasted into chat. **Rotation of the exposed key itself deliberately deferred** (user's call) until after [Design and build the JSON -> Teamup sync engine](issues/06-build-sync-engine.md) is done, to avoid re-verifying access mid-build -- don't forget to actually do it once that ticket closes.
  - The public website's display (FullCalendar vs. a Teamup embed vs. a redirect) is explicitly out of scope for this map -- see Out of scope.

## Decisions so far

- [Set up local Teamup credentials file](issues/01-teamup-credentials-file.md) — Credentials live in a gitignored `.env` (`TEAMUP_TOKEN`, `TEAMUP_CALENDAR_KEY=<redacted, later proven invalid>`, the latter extracted from the calendar's public share URL); whether that share-link key is the same key the API expects is still unverified.
- [Survey Python client options for Teamup's API](issues/03-survey-python-teamup-client-options.md) — No trustworthy maintained Python client library exists; call Teamup's REST API directly via `requests` (a directly-fetchable OpenAPI spec confirms the `remote_id`/`rrule` field names).
- [Obtain a real Teamup Access Key](issues/04-real-teamup-access-key.md) — A real `ks`-prefixed public-link key replaced the invalid share-URL slug in `.env`; read access confirmed (`200 OK`). Superseded by ticket 05's key (below) once write access turned out to be denied.
- [Obtain a write-capable Teamup Access Key](issues/05-write-capable-access-key.md) — The earlier key's read-only-ness was a UI-navigation issue, not a Teamup limitation: "Add User" also contains a "Link" sub-option scoped per-calendar with a chosen permission level, separate from account-based users. A new "Modify"-level link's key now works: confirmed with a full write round-trip (create returned `201`, delete returned `200`, calendar left clean).
- [Confirm Teamup's real API behavior](issues/02-confirm-teamup-api-behavior.md) — **Resolved**, all 6 questions live-tested with real create/read/update/delete calls (recurring series included) and cleaned up afterward. Headline results: create/recurrence/field-mapping work as spec-described; upsert does **not** self-dedupe (duplicate `remote_id` POST -> `400 event_not_unique`, so the sync engine must list-then-branch create/update itself); `remote_id` round-trips on list/read; delete-by-`remote_id` works via query params for one-off events but not for recurring series (use internal id + `redit=all` there instead, resolved via the same list call used for upsert detection). Corrected finding: `tz` is a **fixed calendar-level property**, not derived from the offset in `start_dt`/`end_dt` as the ticket-05 smoke test guessed (three different offsets all returned the same `tz`) -- see [the findings file](../../docs/research/teamup-live-api-behavior.md) for full detail.
- [Design and build the JSON -> Teamup sync engine](issues/06-build-sync-engine.md) — **Resolved.** `scripts/teamup_client.py` + `scripts/sync_teamup.py` built, unit-tested (25 tests, mocked HTTP) and integration-tested (2 tests, real API round trip with a throwaway tagged fixture), then **run for real**: `make sync-teamup` created all 8 real events from `data/events.json` on the real calendar (0 skipped), verified present via a follow-up `GET /events` and confirmed idempotent on a second run (`0 created, 8 updated, 0 deleted`). One deviation from this ticket's own assumption, found via live smoke-testing done as part of this ticket: in-place `PUT .../{id}?redit=all` editing of a recurring series is **unsafe** (silently dropped an occurrence in testing, and separately hit a real Teamup `500 Maintenance In Progress`) -- a changed weekly event is instead deleted (`redit=all`) and recreated via `POST`, both proven-reliable operations; a changed one-off event still uses a normal `PUT` (confirmed idempotent-by-internal-id, and confirmed Teamup requires the body's own `id` field to match the URL's, which the prior research hadn't exercised).

**Map destination reached**: the real Teamup calendar is now populated with all 8 real events from `data/events.json`, matching it exactly (verified by `remote_id`), and no tickets remain open. The one loose end outside this ticket's own scope is the deferred rotation of the first Modify-permission key noted above (was deliberately postponed until this ticket closed).

## Not yet specified

- Error handling / partial-failure behavior during a sync run (e.g. a Teamup API call fails partway through a multi-event sync) -- [ticket 06](issues/06-build-sync-engine.md) closed without addressing this explicitly; still not sharp enough to ticket, and now that the map's destination is reached, would only matter for a future effort (e.g. hardening the sync for unattended/scheduled runs, itself out of scope here -- see Out of scope).

## Out of scope

- **Public website display change** (FullCalendar vs. Teamup embed vs. a redirect to Teamup) -- ruled out during destination-naming. The user expects natenite.net's calendar link will likely just redirect to Teamup eventually, but that's a separate future effort, not part of this sync engine.
- **Ongoing/scheduled re-sync automation** (cron, CI running the sync on a timer or on every data change) -- beyond this map's finish line (one successful real sync populating the calendar); a candidate for a future effort once the engine itself is proven.
- **Two-way sync / reconciling manual edits made directly in Teamup's UI** -- ruled out; JSON is the sole source of truth.
- **Multi-sub-calendar routing** -- ruled out; a single flat Teamup calendar is in use.
- **Retiring `hugo-natenite.net`'s old pipeline** (removing its `data/events.json`/`sync_calendar.py`/`static/events.ics`) -- the user said this will happen eventually, but it's a cleanup in a different repo, not part of this map's destination.
